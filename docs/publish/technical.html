01아키텍처

OS Monitor는 클러스터에 이미 있는 관측 스택(Prometheus, Loki)을 데이터 소스로 씁니다. 수집기가 60초마다 PromQL로 노드 지표를 읽어 TimescaleDB에 쌓고, 분석 작업이 그 위에서 위기 감지와 예측을 수행합니다. 사용자는 API를 통해 대시보드·CLI·리포트로 결과를 봅니다.

API는 로그를 조회할 때 Loki에 직접 LogQL을 보냅니다. 메트릭은 DB에서 읽습니다. 따라서 DB가 수집 이력의 진실 소스이고, Prometheus는 실시간 소스입니다.

03수집

PrometheusCollector.collect_all()이 아래 쿼리를 병렬로 실행하고, 결과를 instance 라벨로 노드에 매핑합니다. 지표가 없으면 0이 아니라 null로 저장해서, 정상값으로 잘못 보이지 않게 합니다.

필드PromQL
cpu_usage100 - avg by(instance)(rate(node_cpu_seconds_total{mode="idle"}[5m]))*100
memory_usage(MemTotal - MemAvailable) / MemTotal * 100
disk_usage루트(/) 파일시스템 (size - avail) / size * 100, tmpfs 제외
load1·5·15node_load1, node_load5, node_load15
cpu_corescount by(instance)(node_cpu_seconds_total{mode="idle"})
load_per_coreload1 / cpu_cores (수집기에서 계산)
procs_runningnode_procs_running
procs_zombiesum by(instance)(node_processes_state{state="Z"}) or (0 * count by(instance)(node_processes_state))
inode_usage(1 - files_free / files) * 100, 루트 파일시스템
uptime_sectime() - node_boot_time_seconds
os_distro·kernelnode_os_info의 pretty_name, node_uname_info의 release 라벨
network·disk I/Orate(..._bytes_total[5m]), lo 인터페이스 제외
좀비 프로세스 지표는 Node Exporter의 --collector.processes가 켜져 있어야 나옵니다. 좀비가 0개면 state="Z" 시계열 자체가 없으므로, 수집기가 켜진 노드에서는 or 절로 0을 채웁니다.

스키마는 멱등입니다(CREATE ... IF NOT EXISTS, ADD COLUMN IF NOT EXISTS). API와 Collector 중 먼저 뜨는 쪽이 적용합니다. 별도 마이그레이션 도구는 쓰지 않습니다.

리포트 본문은 파일이 아니라 DB에 저장합니다. API가 여러 Pod로 떠 있고 CronJob Pod와 저장소를 공유하지 않기 때문입니다.

05분석

위기 감지

수집할 때마다 노드별로 임계값을 검사하고, 넘으면 events에 기록합니다. crisis_engine은 같은 시간대의 Loki 로그를 붙여 진단하고, crisis_catalog의 원인·해결 방법·공식 문서 링크를 제시합니다.

유형지표경고 / 위험
HIGH_CPUcpu_usage_ratio80 / 90 %
MEMORY_EXHAUSTIONmemory_usage_ratio80 / 90 %
DISK_FULLdisk_usage_ratio75 / 90 %
HIGH_LOADload_per_core1.5 / 2.0

로그 분석

log_service는 LogQL로 최근 로그, 우선순위·노드별 요약, 알려진 이상 징후 9가지(OOM, 커널 패닉, I/O 오류, 파일시스템 오류, 디스크 공간 부족, segfault, hung task, 인증 실패, 서비스 기동 실패)를 정규식으로 찾습니다. 결과는 sum by(node_name)로 노드별 건수를 냅니다.

예측

최근 30일의 일 단위 평균에서 IQR 기준 이상치를 뺀 뒤 선형 회귀로 기울기를 구합니다. 7·30·90일 뒤 값은 0~100으로 자르고, 기울기가 양수이면 100%까지 남은 일수를 계산합니다.

데이터 포인트confidence
30 이상high
14 ~ 29 (기울기가 0.01 미만이면 high)medium
3 ~ 13low
1 ~ 2 (기울기 0, 현재값 유지)very_low

06API

모든 경로는 /api/v1 아래에 있고, 로그인과 헬스체크를 뺀 나머지는 세션 토큰(Authorization: Bearer)이 필요합니다. 속도 제한(slowapi)과 CORS가 적용되고, OpenAPI 문서가 자동 생성됩니다.

메서드경로설명
GET/clusters, /clusters/{c}, /clusters/{c}/nodes클러스터 목록, 최신 지표와 이벤트, 노드 정보
GET/metrics/os/{c}/{node}노드 시계열 (interval 1h 이상은 시간 집계 사용)
GET/metrics/summary/{c}, /metrics/top최근 10분 최신값, 상위 노드
GET/events, /events/{id}위기 이벤트 목록과 상세
GET/predictions/{c}, /predictions/{c}/{node}예측과 권고
GET·POST/reports, /reports/{id}/download, /reports/{id}/view, /reports/generate리포트 목록, 다운로드, 미리보기, 생성
GET/logs, /logs/summary, /logs/patternsLoki 프록시: 로그, 요약, 이상 징후
POST·GET/auth/login, /auth/logout, /auth/me, /auth/change-password세션 인증
GET·POST/auth/ui/session, /auth/ui/users, /auth/ui/password공용 UI 계정·페이지 권한
GET/healthzDB에 SELECT 1까지 실행, 실패하면 503

07인증과 권한

  • 비밀번호: PBKDF2-HMAC-SHA256과 사용자별 salt로 저장합니다. 평문은 저장하지 않습니다.
  • 세션: 로그인하면 임의 토큰을 발급해 sessions에 저장합니다. 비밀번호를 바꾸면 그 사용자의 세션을 모두 지웁니다.
  • 시드 계정: 처음 기동할 때 ADMIN_USERNAME/ADMIN_PASSWORD로 관리자를 만듭니다. 값을 주지 않으면 기본값을 씁니다.
  • 페이지 권한: page_policy가 앱별 페이지 목록과 규칙을 정의합니다. admin은 전부, viewer는 허용된 페이지와 settings만 접근할 수 있고 users는 쓸 수 없습니다. UI와 서버가 같은 규칙을 씁니다.

08배포

deploy/가 GitOps의 단일 진실 소스입니다. ArgoCD Application os-monitor-prod가 deploy/overlays/prod를 main 브랜치에서 자동 동기화합니다(auto-sync, selfHeal, prune).

# 1) 이미지 빌드·푸시 (태그 = git short SHA)
docker build -f Dockerfile.collector -t registry.local.cloud:5000/os-monitor/collector:<sha> .
docker push registry.local.cloud:5000/os-monitor/collector:<sha>

# 2) 태그 갱신 후 main에 반영
#    deploy/overlays/prod/kustomization.yaml → images[].newTag: "<sha>"
git commit -am "chore: bump collector to <sha>" && git push

# 3) ArgoCD가 감지해 롤아웃 (기본 3분 폴링)
이미지Dockerfile포함
apiDockerfile.apiFastAPI 서버
collectorDockerfile.collector수집기, 예측·리포트 CronJob
dashboardDockerfile.dashboardnginx와 정적 자산. entrypoint.sh가 API 기본 경로를 주입

CI 서비스(GitHub Actions)는 쓰지 않습니다. 빌드는 운영 서버에서 직접 하고, 배포는 Git 커밋만으로 일어납니다.

09보안 설계

영역설계상태
노드 접근SSH 수집을 없애고 Node Exporter 지표만 씁니다. 노드 계정이나 키를 배포하지 않습니다.적용
비밀값Sealed Secrets 컨트롤러(kube-system)의 공개키로 암호화한 SealedSecret만 Git에 둡니다. scripts/seal-secrets.sh는 값을 출력하지 않고 파이프로만 넘깁니다.봉인 대기
소스 저장소 인증remote URL에서 토큰을 지우고 gh 자격 헬퍼를 씁니다. 범위를 좁힌 fine-grained 토큰으로 교체할 예정입니다.교체 대기
사용자 인증PBKDF2 해시, 세션 토큰, 서버 측 페이지 권한 검사적용
로그 개인정보저널에는 인증 기록이 들어 있을 수 있습니다. UI는 우선순위와 징후 중심으로 보여 줍니다. 필요하면 promtail 파이프라인에서 걸러 냅니다.적용

운영 절차는 저장소의 docs/security.md와 deploy/sealed-secrets/README.md에 있습니다.

10운영과 관측

  • 프로브: API와 대시보드에 liveness·readiness 프로브가 있습니다. API 프로브는 DB 연결까지 확인합니다.
  • 알림 규칙: PrometheusRule OSMonitorAPIDown, OSMonitorDashboardDown(kube-state-metrics 기반).
  • Node Exporter 설정: 공용 prometheus-stack에 --collector.processes를 추가했습니다(deploy/monitoring/, --reuse-values로 적용).
  • 테스트: make lint(ruff), make test-unit(pytest), make test-integration(실제 DB·Prometheus·Loki 연동).

11제약과 과제

  • Alertmanager에 수신처가 없어서, 알림 규칙은 평가되지만 어디에도 전달되지 않습니다.
  • 노드 목록(NODE_MAP)이 코드에 고정돼 있습니다. 노드를 늘리거나 줄이면 코드를 바꿔야 합니다. Prometheus target에서 자동으로 찾도록 바꾸는 것이 다음 과제입니다.
  • 호스트 저널 promtail과 ArgoCD 노출용 프록시는 ArgoCD가 관리하지 않는 수동 리소스입니다.
  • API 이미지를 다음에 빌드해야 최신 지표 응답에 inode·uptime·프로세스 필드가 포함됩니다.
  • 단위 테스트 2건(인증 401, 예측 데이터 부족 기대값)이 현재 코드 동작과 맞지 않아 갱신이 필요합니다.
